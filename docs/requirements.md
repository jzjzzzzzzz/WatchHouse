# 开发与提交要求

## 提交日期

Git commit history 的日期范围必须在 **2026-04-08 到 2026-10-05（含首尾）**。这是对用户“april 8-10.5”的明确解释，按 America/New_York 时区计算。

author date 和 committer date 都必须在范围内。用户进一步要求历史分布在整个区间，目标覆盖约 90% 的天数，活跃日尽量有多个有意义的提交。

区间共 181 天，活跃日目标为 163 天，即 90.06%。初始编排为每个活跃日 3 个独立工作单元，约 489 次提交；这是排期目标，不是为了凑数必须制造的提交数量。如果实际工作不足，公开未达标，或者在用户同意后调整粒度。

**日期采用回溯编排，不代表真实工作发生在这些过去日期。** 每次提交记录 `Actual-Execution-Time`（实际执行时间）和 `History-Schedule: retrospective` trailer。项目实际开始于 2026-10-05；不得声称经历了半年真实运行或维护。实际运行时长和测试时间仍按真实时间记录。

两个尚未发布的初始提交调整至编排起点，保留其原始真实时间到 trailer；原始 main 引用在本地备份。后续使用 scripts/commit-step.py 分配日期并提交。不能修改系统时间，不修改全局 Git 配置。

## 仓库与提交方式

- 在 /Users/jz/watchhouse 创建独立 Git 仓库，默认分支 main。
- 使用现有本机 Git 作者配置，不擅自更改全局配置。
- 暂不设置 remote，不 push。
- 每次提交一个可解释的工作单元；代码提交包含相应测试，文档明确哪些能力未实现。
- 不创建占位提交，不把回溯日期当作真实开发耗时。每个工作单元都需实际发生并能通过 diff 解释。
- 提交前检查 diff、测试结果、秘密和日期；pre-commit hook 作为本地防误操作措施，不能当作不可绕过的安全控制。
- 禁止提交真实凭证、生产日志、备份、toolchain 或编译产物。

## 日期编排与核验

163 个活跃日均匀分布于 181 天区间，包含首日和末日，18 天留空。每天安排三个时隙，时区 America/New_York；不伪装成精确的真实工作时刻。

根据用户追加要求，后续时隙在当天 08:00:00 至 22:59:59 内随机分配时、分、秒，按时间排序，间隔至少 20 分钟，不再固定为 09:00、13:00、17:00。随机种子绑定日期和编排版本，使同一时隙在检查或重试时保持稳定。已有九个提交的日期不重写；随机化从第十个提交开始。随机时间仍然是回溯编排，不是实际执行时间。

提交脚本只提交已经 staged 的非空改动，不自动写功能、不自动填充日期、不 push。脚本耗尽时隙时停止。提交量达到完整目标之前，日期覆盖率只能称为进度，不能称为已完成。

pre-commit 检查 author/committer 日期、实际时间 trailer 参数和日期顺序。钩子只防误操作，Git 的历史和贡献图不是能力证明；测试与部署证据才是。

## 开发顺序

1. 固定事件和响应契约，建立场景目录。
2. 实现只读解析与采集，并测试 malformed、权限不足和未知归属。
3. 实现本地持久化、上报、控制面和规则。
4. 只在前面验证可靠后加入审批与固定写动作。
5. 在真实 Linux VM 上验证，再进行部署、恢复和长期运行。

Mac 上的 fixture 测试和 Linux 交叉编译不能标为真实 VPS 验收。当前优先得到可运行、可测试的小切片，不宣称整个平台完成。
