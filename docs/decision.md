# 项目选题决定

## 判断标准

按以下顺序选题：真实长期用途、可直接核验的工程证据、Cybersecurity 与 Operations 的结合深度、独立核心、可逐步交付。技术数量和界面效果不作为首要标准。

## 四个候选

### 候选一 服务感知的 Linux 安全与恢复闭环

- 一句话定义：把真实 Linux 安全事件和服务故障转化为带证据、受限、可验证的响应与恢复。
- 实际用途：维护自己的 VPS、反向代理和自托管服务，处理异常认证、暴露漂移、错误配置和恢复演练。
- 技术难度：高，主要难在状态一致性、系统归属、权限边界、断网重试和失败恢复，不在 UI。
- 网安证据：检测规则、威胁模型、最小权限、主机身份、审批绑定、越权拒绝、调查时间线。
- 运维证据：systemd、journald、TCP 监听、Docker 网络、Nginx/TLS、PostgreSQL、备份恢复、故障排查。
- 最大风险：范围膨胀成 SIEM + SOAR + 管理面板，或控制端变成远程 root shell。
- 区别：不重写 Wazuh、Fleet、Cockpit；用少量真实场景证明事件到服务恢复的完整性。

### 候选二 自托管服务的灾难恢复验证器

- 一句话定义：定期把真实备份恢复到隔离环境，以业务检查而不是 backup exit code 判断可恢复性。
- 实际用途：验证自己的 PostgreSQL、服务配置、持久卷及密钥恢复流程。
- 技术难度：中高，一致性、依赖顺序、隔离、数据验证和 RPO/RTO 测量都有实际难度。
- 网安证据：备份凭证隔离、恢复环境边界、秘密恢复、证据完整性、勒索事件后的恢复设计。
- 运维证据：数据库、存储、自动化、网络重建、故障注入和恢复 runbook。
- 最大风险：成为 restic 的调度包装；若没有真实应用恢复，技术深度不足。
- 区别：restic 提供备份引擎，本项目提供应用级恢复证明。

### 候选三 运行资产感知的漏洞修复交付系统

- 一句话定义：把 SBOM/CVE 与实际运行服务、网络暴露和发布版本关联，完成补丁验证及回滚。
- 实际用途：管理自己的容器更新，区分“扫描发现”与“当前部署确实存在风险”。
- 技术难度：高，资产关联、版本追踪、发行版修补信息和发布安全需要严谨处理。
- 网安证据：漏洞 triage、供应链、风险排序、secret 检测、授权发布。
- 运维证据：CI/CD、镜像构建、数据库迁移、健康检查、更新和回滚。
- 最大风险：没有足够可信的数据就声称漏洞不可达；或只是调用 Trivy 再展示表格。
- 区别：复用 Trivy 的发现，自己做运行上下文与修复交付，不做新的 scanner。

### 候选四 小规模云和 VPS 暴露面验证系统

- 一句话定义：对照声明的 DNS、TLS、端口和访问策略，从外部与主机内部共同确认实际暴露面。
- 实际用途：发现错误端口发布、IPv6 遗漏、过期证书、代理绕过和云防火墙漂移。
- 技术难度：中高，网络视角、NAT、容器转发、DNS 和服务身份关联是真正难点。
- 网安证据：暴露面管理、网络分区、安全不变量和攻击路径分析。
- 运维证据：TCP/IP、DNS/TLS/HTTP、Docker、防火墙、云 API 与故障定位。
- 最大风险：退化成 port scanner；公网不可达也不能证明所有网络位置不可达。
- 区别：不是扫描更多端口，而是解释配置、系统状态与外部观测为何一致或冲突。

## 最终选择

**PROJECT: Watchhouse — Linux 安全事件与服务恢复闭环**

选择候选一。其他候选不是差项目，但单独做时证明范围更集中：恢复验证偏运维；漏洞修复偏供应链与发布；暴露面验证偏网络。Watchhouse 能以同一条业务链路自然涉及这些能力，而不是为 checklist 拼装组件。

其中，候选二的隔离恢复和候选四的外部验证只取必要的小部分。候选三放到后续，不把第一版扩大成全栈安全平台。

## 真正自己实现的核心

1. 有来源和可信度标记的事件、资产、finding 数据模型。
2. 日志与服务上下文的关联，以及不确定归属的表达。
3. 绑定证据和前置条件的响应计划。
4. 拒绝任意 shell 的主机侧动作接口。
5. 持久化状态、幂等执行、过期拒绝、重启恢复。
6. 内部与外部验证、失败回滚、明确的回滚失败状态。
7. 可复现的攻击、防御、故障和恢复测试。

部署自动化、备份存储、加密、指标系统不是重新发明的目标。

## 实际用途

长期运行在自己的服务器上，回答日常问题：这个监听端口属于谁？SSH 异常之后是否出现成功登录？502 是 upstream、进程、配置还是网络故障？变更后 TLS 和应用是否真的恢复？最近的备份实际能恢复到什么时间点？

运行环境不是临时 DVWA。选一项本来就要使用的自托管服务作为 workload，故障注入只在 staging 副本执行，日常生产只读监测起步。

没有证据证明这是商业市场空白。它有明确的个人与小团队用途，也有足够独立工程量。最有说服力的成果是连续使用记录和真实 postmortem，而不是声称替代企业 SIEM。

## 不做什么

第一版不做 Kubernetes、多云、AI 归因、通用规则 DSL、eBPF 探针、完整 EDR、任意远程命令、自动封 IP、自动漏洞升级、复杂 dashboard。

不声称抵御已经控制 root 的攻击者，不把时间相关性写成攻击因果，不把规则命中率等同于真实世界检出率。
